# 51Talk 课件生成器 — 技术方案对比

## 三种方案概览

| | 方案 A：Python 脚本（写死版式） | 方案 B：Python + Jinja2 模板 | 方案 C：基于 presentation-ai |
|---|---|---|---|
| **核心思路** | 排版逻辑写死在 Python 函数里，AI 只生成内容 | 排版写在 HTML 模板文件里，AI 填充数据 | 基于现有 Next.js 全栈项目二次开发 |
| **实现难度** | ⭐ 最简单 | ⭐⭐ 中等 | ⭐⭐⭐⭐ 较难 |
| **开发周期** | 1-2 天 | 3-5 天 | 2-4 周 |
| **技术栈** | Python | Python + Jinja2 | Node.js / Next.js / TypeScript / PostgreSQL |

---

## 方案 A：Python 脚本（当前方案）

### 原理
每种版式（warm_up / language_input / grammar_focus…）对应一个 Python 函数，
函数直接拼接 HTML 字符串。AI 生成 JSON 数据，函数负责渲染。

```
用户输入主题
    → AI 生成 JSON（内容）
    → Python 函数渲染 HTML（版式写死）
    → WeasyPrint 导出 PDF
```

### 优点
- 上手极快，代码量少
- 无需额外框架，依赖只有 `openai` + `weasyprint`
- 版式还原度高，完全掌控每个像素
- PDF 导出稳定可靠
- 本地运行，无需服务器

### 缺点
- 改版式需要改 Python 代码，非技术人员无法自助调整
- 无可视化编辑界面，生成后只能看 HTML/PDF，不能点击修改
- 新增版式需要写新函数

### 适合场景
- 版式相对固定（51Talk 课件结构规律）
- 个人/单人使用
- 快速验证效果

## 方案 B：Python + Jinja2 模板

### 原理
将 HTML 版式抽离为独立的 `.html.j2` 模板文件，
Python 只负责调用 AI 和渲染模板，不再硬编码 HTML。

```
用户输入主题
    → AI 生成 JSON（内容）
    → Jinja2 加载对应模板文件（版式）
    → 渲染 HTML → 导出 PDF
```

### 目录结构示例
```
textbook_generator/
├── main.py
├── config.py
├── templates/
│   ├── base.html.j2          # 公共样式（Logo、字体、颜色）
│   ├── cover.html.j2
│   ├── warm_up.html.j2
│   ├── language_input.html.j2
│   ├── grammar_focus.html.j2
│   ├── practice.html.j2
│   └── wrap_up.html.j2
└── output/
```

### 优点
- 改版式只需编辑模板文件，不用动 Python 代码
- 模板文件直观易读，懂 HTML/CSS 即可修改
- 新增版式只需新建一个 `.j2` 文件
- 版式和逻辑分离，代码更整洁

### 缺点
- 需要学习 Jinja2 语法（不复杂，但有学习成本）
- 仍然没有可视化编辑界面
- PDF 导出依然依赖 WeasyPrint

### 适合场景
- 版式需要经常微调
- 有人负责维护模板样式
- 希望非开发人员也能改版式

## 方案 C：基于 presentation-ai 二次开发

### 原理
Fork presentation-ai（开源 Gamma 替代品），在其 Next.js 全栈框架上：
- 新增 51Talk 主题
- 新增大纲上传功能
- 新增自定义模板风格提取
- 修复/完善 PDF 导出（官方尚未完成）

```
用户在网页界面输入主题或上传大纲
    → AI 生成结构化内容（流式输出）
    → 网页编辑器实时显示，可点击编辑
    → 导出 PDF / PPT（需自行实现）
```

### 优点
- 有完整的**可视化编辑界面**（所见即所得）
- 支持**实时预览**，内容生成过程可见
- 富文本编辑器（Plate.js），可直接在网页上修改文字
- 未来可扩展为多用户 SaaS 平台
- 生态完整（主题系统、拖拽排序、图片插入）

### 缺点
- **PDF 导出功能官方尚未完成**（Roadmap 标注为 🔴 Not Started）
- 需要部署 PostgreSQL 数据库
- 需要配置多个 API（OpenAI / NextAuth / UploadThing 等）
- 二次开发量大，需要熟悉 Next.js / TypeScript
- 51Talk 特定版式需要从零开发 Plate.js 自定义组件
- 运行依赖 Node.js 环境，本地启动较重

### 关键风险
> ⚠️ presentation-ai 的 PDF 导出在官方 Roadmap 中明确标注为
> **"🔴 Not Started — High priority"**
> 意味着这个功能需要你自己实现（用 Puppeteer 或 Playwright），
> 这本身就是一个独立的开发任务。

### 适合场景
- 需要网页可视化编辑界面
- 未来计划开放给多位老师使用
- 有 Web 全栈开发能力
- 不急于 PDF 导出，可以先用浏览器打印

## 综合对比表

| 维度 | 方案 A | 方案 B | 方案 C |
|---|---|---|---|
| **开发难度** | ⭐ 极低 | ⭐⭐ 低 | ⭐⭐⭐⭐ 高 |
| **开发周期** | 1-2 天 | 3-5 天 | 2-4 周 |
| **PDF 导出** | ✅ 稳定 | ✅ 稳定 | ⚠️ 需自行实现 |
| **可视化编辑** | ❌ 无 | ❌ 无 | ✅ 完整编辑器 |
| **版式灵活性** | 低（改代码）| 中（改模板）| 高（拖拽编辑）|
| **51Talk 风格还原** | ✅ 精准 | ✅ 精准 | ⚠️ 需额外开发 |
| **本地运行** | ✅ 轻量 | ✅ 轻量 | ⚠️ 需 Node+DB |
| **扩展性** | 低 | 中 | 高 |
| **单人使用** | ✅ 最优 | ✅ 合适 | ⚠️ 杀鸡用牛刀 |
| **多人协作** | ❌ | ❌ | ✅ |

## 推荐路径

```
现阶段（验证效果）
    → 方案 A：快速跑通，看 AI 生成质量和版式效果

版式需要频繁调整
    → 升级到方案 B：把模板抽离，改样式更方便

未来需要给多位老师用 / 需要网页界面
    → 再考虑方案 C：此时已有成熟的内容生成逻辑可迁移
```

**结论：建议先从方案 A 开始，用最小成本验证核心流程是否满足需求，
再根据实际痛点决定是否升级。**
